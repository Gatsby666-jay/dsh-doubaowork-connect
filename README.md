# dsh-doubaowork-connect · DSH Connect 豆包工作

把本机登录的 **豆包工作**（豆包客户端的「工作」模式）接进 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的模型选择器：模型清单按上游目录刷新，积分倍率由上游给出，支持逐模型图片输入开关、多账号与账号池自动换号，并在设置页与输入框里提供只读的积分读数。

不需要 API key，不需要新建账号：只用你已经登录的那台豆包客户端，或者在设置页里粘贴一次浏览器 Cookie。

```
豆包客户端 / 浏览器登录一次
        │  Cookie（Windows DPAPI 解密，只读）
        ▼
   DSH 插件 ──▶ https://www.doubao.com  （工作模式内部协议，SSE 流式）
        │
        ▼
DSH 模型选择器里出现：豆包 2.1 Lite / DeepSeek V4.1 Flash / Kimi K3 / GLM 5.4 / Qwen 4 Max …
每个模型带一枚由上游给出的倍率徽章：0.05x、0.46x、0.80x、限时优惠 0.01x、免费 …
```

## 功能

- **模型目录来自上游。** 每次刷新读取 `https://www.doubao.com/chat/` 页面里内联的 office 模式模型菜单，解析出模型键、显示名、上下文窗口、推理档位与倍率标签。读不到时依次退到磁盘缓存、内置快照——刷新失败不会让选择器变空。
- **倍率不猜。** 豆包把倍率放在模型条目的 `tag_list` 文案里（`0.65x`、`限时优惠 0.01x`、`新上线 0.80x`、`小额免费`）。插件只解析这段文案，并把上游打印的那一段原样做成徽章（`0.80x` 不会变成 `0.8x`）；上游没给就显示 `—`，从不补一个数字。
- **逐模型图片输入开关。** 默认全部关闭；打开后该模型才在选择器里声明图片能力，也才真的发送图片。打开方式：设置 → 插件 → 豆包工作 → **模型** 分页，每个模型右侧的「图片输入」开关。豆包上游的模型菜单里没有任何图片能力字段（`image_input` 全为 `undefined`），所以插件无法自动判断哪个模型支持图片，只能由你按需开启。
- **多账号 + 账号池。** 池成员是显式勾选，默认一个都不含。池开启时按顺序服务，遇到登录失效 / 要求验证 / 限流就为**这一次请求**换下一个账号，并把失败账号放进冷却。
- **只读积分。** 额度窗口与每日签到状态，卡片与输入框胶囊式读数。
- **两个设置 tab。** 「账号」管登录态与账号池，「模型」管目录与两个开关。

## 安装

需要 DSH 0.1.7 及以上。

**从 GitHub 安装**

```sh
dsh plugin --profile <你的 profile> add github:Gatsby666-jay/dsh-doubaowork-connect
```

或在 DSH 桌面端 **设置 → 插件** 里填同一来源。装完刷新页面或重启一次宿主，模型选择器里就会出现豆包系列模型。

**从本地目录安装（开发调试用）**

```sh
cd ~/.dsh/profiles/<你的 profile>
pnpm remove dsh-doubaowork-connect && pnpm add link:/绝对路径/dsh-doubaowork-connect
```

用 `link:` 是为了改完源码不用重新安装。这个插件**零依赖**：不 import 任何第三方包，只用到宿主提供的服务与 Node 内置模块，所以不存在 peer 包解析问题。

## 账号来源

两种方式，都不需要额外安装：

1. **从本机豆包客户端读取**（推荐）。读取客户端 Chromium 配置里的 Cookie 库，用当前 Windows 用户的 DPAPI 解出主密钥，再解出 Cookie。客户端开着也能读——库被独占时先复制一份再解析。若某个配置读不出来，页面会把**具体原因**列出来（占用、没有会话、app-bound 加密）。
2. **粘贴 Cookie。** 从已登录的 `www.doubao.com` 页面复制 Cookie 请求头，至少需要 `sessionid`。

账号存进插件自己的状态文件 `$DSH_HOME/.doubaowork.cn.json`（权限 600）。导入后与客户端解耦：客户端退出登录、切号、卸载都不影响已导入的账号；只有 Cookie 在服务端过期才需要重新登录。

## 账号池规则

- **池关着**：当前选中的账号服务所有请求。
- **池开着**：勾选的账号按顺序服务。某个账号登录失效、被要求人工验证或限流时，**这次请求**自动换下一个账号；失败账号进冷却（失效 12 小时、验证 30 分钟、限流 3 分钟）。
- **网络错误与上游格式错误不换号。** 那与账号无关，换号只会重复失败，因此直接把错误交给用户。

「清除冷却并重试」会清空所有冷却并把积分与签到重新读一遍，处理完验证或重新登录后立刻能看到结果。

## 积分与签到：只读

- 额度来自 `/alice/commerce/sale/subscription/quota/summary/`，按上游给的窗口原样展示，不自行换算、不编造单价。上游没报的金额显示 `—`，不显示 `0`：把「没报」画成「用完」会让人以为额度见底。
- 签到状态来自活动详情里的 `daily_checkin` 节点（今日是否已签、连续天数、可领额度）。

**插件不代签。** 网页会话无法签到，而且一次失败的代签请求会导致当天额度作废、不可补救（实测拿到 `710010702` 之后客户端里再点签到会提示「当前暂不符合领取条件」）。所以这里只显示状态，签到请去豆包客户端完成。

## 设置页

| Tab | 内容 |
| --- | --- |
| 账号 | 导入 / 粘贴账号、切换、重命名、移除、账号池开关与成员、积分与签到读数 |
| 模型 | 目录来源与刷新时间、每个模型的倍率徽章、上下文与推理档位、显示开关、图片输入开关 |

输入框右侧还有一颗胶囊式读数，点开显示账号、剩余积分、对应额度窗口、签到状态与读数更新时间。胶囊每 60 秒读一次本地状态，额度超过 90 秒才回上游刷新，所以长时间开着也不会显示很久以前的数据。

## 实现要点

- **零构建、零运行时依赖**，纯 ESM。宿主半边注册 `llm` provider + 自己的 loopback JSON 路由；浏览器半边通过 `window.__ModuleLoader__.load` 注册 `settings.section` 与 `conversation.input.right` 两个插槽，不需要打包器。
- **适配器按契约实现**（`providerInfo` / `providerRetryPolicy` / `listModels` / `resolveModel` / `prepareCall` / `stream`）。流式部分把豆包的 SSE 事件泵成 DSH 的 `StreamChunk`，正文与思考分开成两条 delta。
- **目录刷新会清理已下架的模型**，避免一个停用的模型继续挂着旧倍率——那等于在报一个并不存在的价。
- **积分读数按发起请求时的账号归属**，中途切号不会把 A 号的读数记到 B 号名下。

## 已知边界

- 豆包没有对外开放的 API，这里用的是客户端自己走的内部协议，随客户端版本变化可能失效（验证于 2026-11）。
- 遇到风控（`710022004` 这一类）时，去 `https://www.doubao.com/chat/` 手动发一句话完成验证；验证通过前反复重试只会延长限制。
- 若客户端 Cookie 使用 app-bound 加密（`v20` 前缀），插件进程解不开，会明确报错并在页面上显示原因；此时在客户端里退出再登录一次（会换回 `v10`），或改用粘贴 Cookie。
- 图片输入需要先把图片上传到豆包存储再随请求发送，上传按账号隔离。上传的存储域名由豆包每次动态给出（实测出现过 `snssdk.com`、`bytedancevod.com`、`vodupload.com`、`byteimg.com`），插件按形状校验并钉住 ByteDance 父域，不会把凭证发给别处。
- 视觉能力取决于具体模型，上游没有声明可查。实测同一张图（数字 6284）各问三次：GLM 5.3 Flash 3/3 正确，DeepSeek V4.1 Flash 2/3，MiMo V2.6 Flash 2/3。也就是说「图片能送到模型」和「模型认得准」是两件事，后者由模型自己决定。
- 会话记录会落在豆包账号会话列表里（这就是走客户端同一条服务端接口的固有行为，插件无法关闭服务端留痕）。
- **工具调用走文本信封**：上游没有 OpenAI 式的 `tool_calls`，插件在系统提示里注入一份 JSON 契约，再从回复里解析出来转成真正的工具调用。长上下文与复杂工具组合下不如原生 function calling 稳。

## 隐私

- 登录态只存本机 `$DSH_HOME/.doubaowork.cn.json`（权限 600），不上传。
- 无遥测，不访问豆包之外的域名（图片上传走豆包返回的存储域名，只带短期凭证）。
- 设置页的 HTTP 接口要求 `Host` 是本机回环地址，并在带 `Origin` 时要求同为回环：这挡住了「别处网页驱动这些接口」这个真正要紧的场景（浏览器必定发送自己的 Origin，且网页无法伪造 Host）。同机上的非浏览器进程仍可调用——插件跑在用户自己的会话里，没有更强的身份可校验。

## 与 WorkBuddy 插件的关系

功能形态参照 [dsh-connect-workbuddy](https://github.com/dingminhua/dsh-connect-workbuddy)（同样的产品思路：上游目录驱动倍率、账号池、只读积分胶囊）。豆包的上游协议与它完全不同，这里是从零实现的。

另注：GitHub 上另有一个同名项目 `Joseph2Young/dsh-connect-doubaowork`，与本仓库**没有关系**——命名撞车是因为「仿 dsh-connect-workbuddy + 服务叫豆包工作」这三件事撞到一起，并非同一份代码。
